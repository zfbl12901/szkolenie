### 1. EXPLAIN / EXPLAIN ANALYZE

PostgreSQL provides two essential commands to understand and optimize query performance: **EXPLAIN** and **EXPLAIN ANALYZE**.

---

#### 1.1 EXPLAIN

- **Objective** : see the **estimated execution plan** by the PostgreSQL planner **without executing the query**.  
- Useful for analyzing the estimated cost of a query and anticipating bottlenecks before it touches large volumes of data.  

**Example :**

```sql
EXPLAIN SELECT * FROM orders WHERE order_date >= '2025-01-01';
```

**Typical result :**

```
Seq Scan on orders  (cost=0.00..431.00 rows=20 width=120)
```

- **Seq Scan** : the planner estimates that a sequential scan is necessary.
- **Cost** : execution cost estimate, from start (0.00) to end (431.00).
- **Rows** : estimated number of rows returned (here 20).

Note: these figures are estimates based on statistics and may diverge from actual results if statistics are not up to date.

---

#### 1.2 EXPLAIN ANALYZE

- **Objective** : actually execute the query and provide real times, number of rows processed, and loops for each plan node.
- Allows comparing estimates vs reality, which is crucial for effective optimization.

**Example :**

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE order_date >= '2025-01-01';
```

**Typical result :**

```
Seq Scan on orders  (cost=0.00..431.00 rows=20 width=120) 
(actual time=0.012..0.034 rows=18 loops=1)
```

- **Actual time** : real execution time (start..end) for this node.
- **Actual rows** : actual number of rows processed (here 18 instead of the 20 estimated).
- **Loops** : how many times the operation was repeated (1 here, but can be more for subqueries or joins).

---

#### 1.3 Most common scan types

| Scan | Description | When it appears |
|------|-------------|-----------------|
| **Seq Scan** | Sequential read of the entire table | Small table or no relevant index |
| **Index Scan** | Read via an index to filter rows | Filtering on indexed columns |
| **Bitmap Index Scan** | Combination of indexes and memory page reads | When multiple indexes or value ranges are used |
| **Index Only Scan** | Read only via the index, without accessing the table | If all necessary columns are in the index |

---

#### 1.4 Understanding loops and rows

- **Loops** : number of iterations of the operation.
  - For example, for a nested loop join, the backend may execute the same operation multiple times for each row of the outer table.
- **Rows** : number of tuples processed at each step.
  - Identifying nodes where `rows` or `loops` are very high helps locate bottlenecks.

**Nested loop example :**

```
Nested Loop  (cost=0.85..431.00 rows=20) (actual time=0.012..0.034 rows=18 loops=10)
```

Here, the loop was executed 10 times, which may indicate an inefficient join or a missing index.

---

#### 1.5 Best practices

- Always compare `EXPLAIN` vs `EXPLAIN ANALYZE` to check if the planner is wrong in its estimates.
- Regularly update statistics with `ANALYZE`.
- Try to transform an expensive Seq Scan into Index Scan or Bitmap Scan if possible (see [section 3. Scan types](#3-scan-types)).
- Identify expensive joins and check if an index or materialized CTE can reduce the number of loops (see [section 2. Join types](#2-join-types) and [section 6. CTE](#6-cte-common-table-expressions)).
- For large volumes, generate the JSON plan and analyze it on explain.dalibo.com to visualize the tree and detect expensive nodes.

---

#### 1.6 Visual analysis with explain.dalibo.com

To best exploit execution plans, PostgreSQL allows generating the plan in **JSON** format, which can then be visualized graphically via [explain.dalibo.com](https://explain.dalibo.com/).

##### 1.6.1 Generate JSON plan

```sql
EXPLAIN (ANALYZE, COSTS, BUFFERS, FORMAT JSON)
SELECT *
FROM orders
WHERE order_date >= '2025-01-01';
```

- **ANALYZE** : executes the query to get real times.
- **COSTS** : includes estimated costs in the plan.
- **BUFFERS** : includes information on cache usage.
- **FORMAT JSON** : allows exporting the plan as JSON compatible with explain.dalibo.com.

##### 1.6.2 Exploit the plan on Dalibo

1. Copy the JSON generated by PostgreSQL.
2. Paste the JSON on explain.dalibo.com.
3. Visualize the plan as a graphical tree.
4. Identify expensive nodes thanks to the following information:
   - **Total cost vs Actual time** : difference between estimate and reality.
   - **Rows vs Actual rows** : estimated rows vs processed rows.
   - **Loops** : operation repetitions, indicator of expensive joins.
5. Compare before/after optimization to measure the impact of changes (indexing, query rewriting, partitioning, CTE).

##### 1.6.3 Best practices with Dalibo

- Always generate the JSON plan for critical queries on large volumes.
- Verify that expensive operations identified correspond to observed bottlenecks.
- Use the graphical tree to explain optimizations to the team or document improvements.
- Couple Dalibo analysis with PostgreSQL statistics (`ANALYZE`, `pg_stat_statements`) for complete understanding.

---

### ✅ Key takeaways

- `EXPLAIN` = estimated plan, `EXPLAIN ANALYZE` = real plan.
- `Loops` and `rows` show repetition and real data volume.
- Scan and join types determine query efficiency (see [section 3. Scan types](#3-scan-types) and [section 2. Join types](#2-join-types)).
- Careful reading of the plan allows quickly identifying possible optimizations.

### 2. Join types

When joining multiple tables, PostgreSQL chooses a **join type** based on table size, index presence, and statistics. Understanding these join types is essential for optimizing queries on large volumes.

---

#### 2.1 Nested Loop Join

- **Principle** : PostgreSQL scans **each row** of the outer table (A) and searches for matches in the inner table (B).  
- **Operation** :
  1. For each row of A, perform a search on B.  
  2. Combine matching rows.  
- **When used** :  
  - Small or medium tables.  
  - When the inner table has an **efficient index** on the join key.  
- **Advantages** :
  - Simple to understand and reliable.  
  - Efficient if the outer table is small.  
- **Disadvantages** :
  - Becomes very expensive if both tables are large and without indexes.

**Example :**

```sql
SELECT *
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE c.region = 'Europe';
```

If `customers` is small and `orders.customer_id` is indexed → Nested Loop is chosen.

---

#### 2.2 Hash Join

- **Principle** : PostgreSQL creates a hash table in memory for the smaller table, then scans the larger table to find matches.
- **Operation** :
  1. Build a hash table for the smaller table on the join column.
  2. Scan the larger table and search each value in the hash table.
- **When used** :
  - For large tables.
  - On equality conditions (`=`) on join columns.
- **Advantages** :
  - Very fast for large volumes if the hash table fits in memory.
- **Disadvantages** :
  - Uses a lot of memory.
  - Not efficient for non-equality joins (`<`, `>`) or for already sorted tables.

**Example :**

```sql
SELECT *
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;
```

If `orders` and `customers` are large → PostgreSQL may choose a Hash Join.

---

#### 2.3 Merge Join

- **Principle** : Both tables are sorted on the join key, then merged by scanning both tables in parallel.
- **Operation** :
  1. Sort A and B on the join key (if not already sorted or indexed).
  2. Scan both tables simultaneously to find matches.
- **When used** :
  - Tables already sorted or indexed on the join key.
  - Often used for large volumes with B-Tree indexes.
- **Advantages** :
  - Very efficient for large sorted tables.
  - Less memory-intensive than Hash Join.
- **Disadvantages** :
  - Requires sorting if tables are not already sorted.
  - Less efficient if only a few rows are needed (small filter).

**Example :**

```sql
SELECT *
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
ORDER BY c.customer_id;
```

PostgreSQL will often use Merge Join if both tables are indexed on `customer_id`.

---

### ✅ Key points to remember

- **Nested Loop** → simple and efficient for small tables or existing indexes.
- **Hash Join** → ideal for large volumes and equalities on join columns.
- **Merge Join** → efficient for already sorted or indexed tables, good memory/performance compromise.
- Understanding the join type allows diagnosing slow queries and deciding on optimizations (index, partitioning, query rewriting).

**💡 Data Engineer use case :** In an ETL pipeline, Hash Joins are often preferred for joining large fact tables with dimensions. If you see many Nested Loops on large volumes, it's a warning signal: check indexes on join keys (see [section 4. Advanced indexing](#4-advanced-indexing)).

### 3. Scan types

Scans are how PostgreSQL reads data from tables to execute a query. The choice of scan has a direct impact on performance, especially on large tables.

---

#### 3.1 Seq Scan (Sequential Scan)

- **Principle** : PostgreSQL reads **all rows** of the table, one by one.  
- **When used** :  
  - Small table or very little filtering.  
  - No index available on the filtered column.  
- **Advantages** : simple, reliable.  
- **Disadvantages** : expensive for large tables, full read even if few rows are needed.

**Example :**

```sql
SELECT * FROM orders WHERE amount > 1000;
```

If `amount` is not indexed, PostgreSQL performs a Seq Scan on the entire table.

---

#### 3.2 Index Scan

- **Principle** : PostgreSQL uses an index to find matching rows.
- **When used** :
  - Filter on an indexed column.
  - Large table, but low proportion of filtered rows.
- **Advantages** : targeted read → less data to read.
- **Disadvantages** : less efficient if the majority of the table is needed, as reads become numerous and random.

**Example :**

```sql
CREATE INDEX idx_orders_amount ON orders(amount);
SELECT * FROM orders WHERE amount > 1000;
```

The index allows quickly locating the concerned rows.

---

#### 3.3 Bitmap Index Scan

- **Principle** : PostgreSQL combines multiple indexes (or value ranges) to create a bitmap, then reads only necessary blocks in memory.
- **When used** :
  - Multiple filters on different indexed columns.
  - Large tables with a large number of rows to retrieve.
- **Advantages** : reduces random disk reads, efficiently combines multiple indexes.
- **Disadvantages** : uses more memory to build the bitmap.

**Example :**

```sql
SELECT * FROM orders
WHERE amount > 1000 AND status = 'active';
```

PostgreSQL can use a bitmap to combine indexes on `amount` and `status`.

---

#### 3.4 Index Only Scan

- **Principle** : PostgreSQL reads only the index without accessing the table if all necessary columns are in the index.
- **When used** :
  - Necessary columns already stored in the index.
  - Very efficient for queries that require only few columns.
- **Advantages** : very fast read → no additional disk read.
- **Disadvantages** : limited to columns present in the index.

**Example :**

```sql
CREATE INDEX idx_orders_amount_status ON orders(amount, status);
SELECT amount, status FROM orders WHERE amount > 1000;
```

PostgreSQL can satisfy the query entirely via the index.

---

#### 3.5 Best practices

- Verify that all filtered or joined columns are properly indexed (see [section 4. Advanced indexing](#4-advanced-indexing)).
- Prefer Index Scan or Index Only Scan on large tables to limit disk reads.
- For combined filters, consider Bitmap Index Scan if multiple columns are involved.
- Use `EXPLAIN ANALYZE` to verify that the chosen scan is adapted to the query and data volume.

**💡 Data Engineer use case :** In a Data Warehouse, analytical queries often filter on dates (ex: `WHERE order_date BETWEEN ...`). An Index Scan or Bitmap Index Scan on a partitioned date column (see [section 5. Partitioning](#5-partitioning)) can drastically reduce execution time of reporting queries.

---

### ✅ Key takeaways

- **Seq Scan** : full read → simple but expensive on large tables.
- **Index Scan** : targeted read → fast if few rows concerned.
- **Bitmap Index Scan** : combines multiple indexes → ideal for large volumes and multiple filters.
- **Index Only Scan** : ultra fast → everything is already in the index, no need to fetch data from the table.

### 4. Advanced indexing

Indexes allow PostgreSQL to quickly find rows matching a given criterion. Understanding different index types and their usage is crucial for optimizing queries, especially on large tables.

---

#### 4.1 Multicolumn indexes

- **Principle** : an index can cover multiple columns.  
- **Column order is critical** : the index is optimized for the most selective columns or columns filtered first.  

**Example :**

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

**Usage :**

```sql
SELECT * FROM orders
WHERE customer_id = 123
ORDER BY order_date;
```

Here, the index is used efficiently because `customer_id` is first.

⚠️ **Warning** : if the query filters only on `order_date`, this index will not be optimal.

---

#### 4.2 Partial indexes

- **Principle** : indexes only a subset of rows matching a condition.
- **Advantages** : reduces index size and speeds up targeted queries.

**Example :**

```sql
CREATE INDEX idx_orders_active
ON orders(order_date)
WHERE status = 'active';
```

**Usage** : PostgreSQL will use this index only for rows where `status = 'active'`.

Ideal for columns with majority non-relevant values.

---

#### 4.3 Expression indexes

- **Principle** : indexes the result of an expression or function applied to a column.
- **Advantages** : allows optimizing queries using frequent transformations.

**Example :**

```sql
CREATE INDEX idx_orders_lower_customer
ON orders(LOWER(customer_name));
```

```sql
SELECT * FROM orders
WHERE LOWER(customer_name) = 'dupont';
```

Here, the query can use the index directly, without recalculating the function for each row.

---

#### 4.4 Specialized indexes : GIN, GiST, BRIN

| Type | Main usage | Examples |
|------|------------|----------|
| **GIN** (Generalized Inverted Index) | Text columns, arrays, JSONB | Keyword search, full-text search |
| **GiST** (Generalized Search Tree) | Geospatial, hierarchical data | PostGIS : spatial indexes, polygons |
| **BRIN** (Block Range Index) | Sequential columns or very large tables | Dates, increasing IDs : very light and fast for ranges |

**Examples :**

```sql
-- GIN for JSONB
CREATE INDEX idx_orders_jsonb
ON orders
USING GIN (data);

-- GiST for geospatial
CREATE INDEX idx_locations_gist
ON locations
USING GiST (geom);

-- BRIN for large tables
CREATE INDEX idx_orders_brin
ON orders
USING BRIN(order_date);
```

- GIN/GiST are more expensive to create but greatly speed up complex queries.
- BRIN is very light and adapted to massive tables with sequential columns.

---

#### 4.5 Best practices

- Choose the index type adapted to data and most frequent queries.
- For large tables, prefer partial indexes and BRIN to reduce size.
- For columns used in functions, create expression indexes.
- Always test with `EXPLAIN ANALYZE` to verify that the index is actually used.

**💡 Data Engineer use cases :** 
- **Partial indexes** : In an ETL pipeline, you may have a logs table with 99% rows `status='processed'` and 1% `status='error'`. A partial index `WHERE status='error'` speeds up diagnostic queries without slowing down writes.
- **BRIN** : For time-series tables (events, metrics), a BRIN index on the timestamp column is very efficient and light, even on billions of rows.
- **GIN for JSONB** : If you store semi-structured data (logs, events), a GIN index on a JSONB column allows fast searches in the structure.

---

### ✅ Key takeaways

- Advanced indexing is a major lever for query optimization on large volumes.
- **Multicolumn** → pay attention to order.
- **Partial** → reduce size and speed up targeted filters.
- **Expressions** → optimize frequent transformations.
- **GIN/GiST/BRIN** → adapted for text, spatial, or large sequential tables.

### 5. Partitioning

Partitioning allows **dividing a large table into several smaller tables (partitions)**, while maintaining a single logical view. This reduces unnecessary scans and improves performance and maintenance.

---

#### 5.1 Why partition ?

- Large tables (millions or billions of rows) become **expensive to scan**.  
- Partitioning allows **limiting reads** to relevant partitions according to the query.  
- Facilitates **maintenance** : deletion or archiving of old data without touching other partitions.  
- Improves **parallelism** during read operations or VACUUM.

---

#### 5.2 Partition types

| Type | Description | Usage example |
|------|------------|---------------|
| **RANGE** | Partition by value ranges | Dates : orders by year |
| **LIST** | Partition by specific values | Countries, regions, categories |
| **HASH** | Partition by hash function | Balanced distribution on IDs |

---

#### 5.3 Creating partitions

**Example : RANGE partition by year**

```sql
-- Main partitioned table
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT,
    order_date DATE NOT NULL,
    amount NUMERIC,
    status TEXT
) PARTITION BY RANGE (order_date);

-- Partition for year 2025
CREATE TABLE orders_2025 PARTITION OF orders
FOR VALUES FROM ('2025-01-01') TO ('2025-12-31');

-- Partition for year 2026
CREATE TABLE orders_2026 PARTITION OF orders
FOR VALUES FROM ('2026-01-01') TO ('2026-12-31');
```

PostgreSQL will automatically choose the appropriate partition based on the `order_date` value.

Only relevant partitions are scanned during the query → performance gain.

---

#### 5.4 Best practices

- Choose partition type based on data nature and queries : RANGE for dates, LIST for categories, HASH for uniform distribution.
- Create local indexes on each partition if necessary (each partition can have its own indexes).
- Limit the number of partitions : too many partitions can harm planner performance.
- Vacuum / analyze : partitions are full tables, remember to maintain statistics.
- Maintenance : drop or detach old partitions rather than deleting millions of rows in the main table.

**💡 Data Engineer use case :** Partitioning is essential for Data Warehouses. For example, partitioning a fact table by month allows :
- **Performance** : Queries filtering on a period scan only concerned partitions.
- **Maintenance** : Easy archiving of old data (detach/drop partitions older than 2 years).
- **Parallelism** : Each partition can be processed in parallel during VACUUM or analyze operations.
- **Scalability** : Managing tables with several billion rows becomes possible.

---

#### 5.5 Query example on partitions

```sql
SELECT *
FROM orders
WHERE order_date BETWEEN '2025-01-01' AND '2025-06-30';
```

PostgreSQL will scan only the `orders_2025` partition, not other years.

Significant gain on massive tables.

---

### ✅ Key takeaways

- Partitioning = dividing a massive table into logical pieces to limit scans and facilitate maintenance.
- Main types : RANGE, LIST, HASH.
- Always combine with adapted indexes and statistics management to optimize queries.

### 6. CTE (Common Table Expressions)

CTEs (Common Table Expressions) allow **structuring and simplifying** complex queries by creating temporary tables for local use in a query.

---

#### 6.1 Basic CTE

- **General syntax** :

```sql
WITH cte_name AS (
    SELECT ...
)
SELECT ...
FROM cte_name;
```

Allows breaking a complex query into more readable and reusable parts.

**Simple example :**

```sql
WITH recent_orders AS (
    SELECT *
    FROM orders
    WHERE order_date >= '2025-01-01'
)
SELECT *
FROM recent_orders
WHERE amount > 1000;
```

Here, `recent_orders` is used only once in the main query.

---

#### 6.2 Materialized CTEs

- **Principle** : PostgreSQL evaluates and stores the CTE result in a temporary structure before using it.
- **Advantages** : useful if you reuse the same CTE multiple times in a complex query.
- **Disadvantages** : can be expensive in memory and time if the CTE is large.

**Example :**

```sql
WITH recent_orders AS MATERIALIZED (
    SELECT *
    FROM orders
    WHERE order_date >= '2025-01-01'
)
SELECT COUNT(*) FROM recent_orders
UNION ALL
SELECT SUM(amount) FROM recent_orders;
```

Here, `recent_orders` is calculated once, then reused for multiple aggregations.

---

#### 6.3 Non-materialized CTEs (inline)

- **Principle** : PostgreSQL integrates the CTE directly into the plan as a subquery.
- **Advantages** : often more performant for simple or large CTEs.
- **Disadvantages** : if you reuse the CTE multiple times, it will be recalculated at each use.

**Example :**

```sql
WITH recent_orders AS NOT MATERIALIZED (
    SELECT *
    FROM orders
    WHERE order_date >= '2025-01-01'
)
SELECT COUNT(*) FROM recent_orders
UNION ALL
SELECT SUM(amount) FROM recent_orders;
```

Here, PostgreSQL can integrate the CTE into the global plan to optimize execution.

---

#### 6.4 Best practices

- For simple filters or transformations, prefer non-materialized CTEs to avoid unnecessarily storing large temporary tables.
- For multiple reuse of the same CTE, consider materialization to avoid recalculating multiple times.
- Always verify impact with `EXPLAIN ANALYZE` : some large queries can become slower with `MATERIALIZED`.
- CTEs are particularly useful for clarifying complex queries before optimization.

**💡 Data Engineer use case :** In an ETL pipeline, CTEs allow structuring transformations :
```sql
-- ETL pipeline example with CTE
WITH raw_data AS (
    SELECT * FROM staging_table WHERE load_date = CURRENT_DATE
),
cleaned_data AS (
    SELECT 
        id,
        TRIM(LOWER(email)) AS email,
        CAST(amount AS NUMERIC(10,2)) AS amount
    FROM raw_data
    WHERE email IS NOT NULL
),
enriched_data AS (
    SELECT 
        c.*,
        d.region
    FROM cleaned_data c
    LEFT JOIN dimension_table d ON c.customer_id = d.id
)
INSERT INTO fact_table
SELECT * FROM enriched_data;
```
This approach facilitates debugging and optimization step by step.

---

### ✅ Key takeaways

- CTE = temporary structure to simplify reading and reuse of subqueries.
- **Materialized** → calculated once, useful for reuse, costs more resources.
- **Non-materialized** → integrated in the plan, often more performant on large volumes if not reused.
- Always test with `EXPLAIN ANALYZE` to choose the best option.

### 8. Pitfalls to avoid and antipatterns

This section presents common errors to avoid when optimizing PostgreSQL queries.

---

#### 8.1 Not updating statistics

**Problem :** Obsolete statistics lead the planner to choose bad execution plans.

**Problematic example :**
```sql
-- Massive data import
COPY orders FROM '/data/orders.csv' CSV HEADER;
-- Forgot ANALYZE → obsolete statistics
```

**Consequence :** The planner may choose a Seq Scan when an Index Scan would be 10x faster.

**Solution :**
```sql
ANALYZE orders;  -- Always after massive import
```

**💡 For Data Engineers :** In an ETL pipeline, schedule an automatic `ANALYZE` after each large data load.

---

#### 8.2 Too many indexes on a heavily modified table

**Problem :** Each index slows down INSERT/UPDATE/DELETE because it must be maintained.

**Problematic example :**
```sql
-- Table with many writes (logs, events)
CREATE INDEX idx_col1 ON events(col1);
CREATE INDEX idx_col2 ON events(col2);
CREATE INDEX idx_col3 ON events(col3);
CREATE INDEX idx_col4 ON events(col4);
CREATE INDEX idx_col5 ON events(col5);
-- 5 indexes on a table with 1000 INSERT/second → significant slowdown
```

**Consequence :** Writes become very slow, the system saturates.

**Solution :**
- Index only columns that are really necessary
- Use partial indexes to reduce size
- Analyze usage with `pg_stat_user_indexes` and remove unused indexes

---

#### 8.3 Multicolumn indexes in wrong order

**Problem :** Column order in a multicolumn index is crucial.

**Problematic example :**
```sql
-- Wrong order : order_date first when we often filter on customer_id
CREATE INDEX idx_orders_date_customer ON orders(order_date, customer_id);

-- Frequent query
SELECT * FROM orders WHERE customer_id = 123;  -- Index not used efficiently
```

**Solution :**
```sql
-- Good order : most selective column first
CREATE INDEX idx_orders_customer_date ON orders(customer_id, order_date);
```

**Rule :** The first column should be the one filtered most often, or the most selective.

---

#### 8.4 Functions in WHERE without expression index

**Problem :** Using a function in WHERE prevents using a standard index.

**Problematic example :**
```sql
-- Standard index
CREATE INDEX idx_orders_email ON orders(email);

-- Query with function
SELECT * FROM orders WHERE LOWER(email) = 'test@example.com';
-- Index not used → Seq Scan
```

**Solution :**
```sql
-- Expression index
CREATE INDEX idx_orders_lower_email ON orders(LOWER(email));
-- Now the query uses the index
```

---

#### 8.5 SELECT * on large tables

**Problem :** Retrieving all columns can prevent Index Only Scan.

**Problematic example :**
```sql
-- Index on (amount, status)
CREATE INDEX idx_orders_amount_status ON orders(amount, status);

-- Query
SELECT * FROM orders WHERE amount > 1000;
-- Index Only Scan impossible because all columns are requested
```

**Solution :**
```sql
-- Select only necessary columns
SELECT amount, status FROM orders WHERE amount > 1000;
-- Index Only Scan possible → much faster
```

**💡 For Data Engineers :** In ETL pipelines, avoid `SELECT *` and explicitly specify necessary columns. This improves performance and maintainability.

---

#### 8.6 Multiple OR without adapted index

**Problem :** Multiple OR conditions can prevent efficient index usage.

**Problematic example :**
```sql
SELECT * FROM orders 
WHERE status = 'active' OR status = 'pending' OR status = 'processing';
-- May force a Seq Scan even with an index on status
```

**Solution :**
```sql
-- Use IN instead
SELECT * FROM orders 
WHERE status IN ('active', 'pending', 'processing');
-- More efficient, can use Index Scan or Bitmap Scan
```

---

#### 8.7 Partitioning without filter on partition column

**Problem :** Forgetting to filter on the partition column cancels benefits.

**Problematic example :**
```sql
-- Table partitioned by order_date
SELECT * FROM orders WHERE customer_id = 123;
-- Scans ALL partitions → no gain
```

**Solution :**
```sql
-- Always include a filter on the partition column
SELECT * FROM orders 
WHERE customer_id = 123 
  AND order_date >= '2025-01-01' AND order_date < '2025-02-01';
-- Scans only the concerned partition
```

**💡 For Data Engineers :** In a Data Warehouse, always include a date filter in queries to benefit from partitioning.

---

#### 8.8 Unnecessary materialized CTEs

**Problem :** Forcing materialization of a simple CTE can slow down the query.

**Problematic example :**
```sql
-- Simple CTE, used only once
WITH filtered_orders AS MATERIALIZED (
    SELECT * FROM orders WHERE amount > 1000
)
SELECT COUNT(*) FROM filtered_orders;
-- Unnecessary materialization → memory and time overhead
```

**Solution :**
```sql
-- Let PostgreSQL decide (or NOT MATERIALIZED if necessary)
WITH filtered_orders AS (
    SELECT * FROM orders WHERE amount > 1000
)
SELECT COUNT(*) FROM filtered_orders;
-- PostgreSQL optimizes automatically
```

---

#### 8.9 Ignoring warning signals in EXPLAIN ANALYZE

**Problem :** Not analyzing gaps between estimates and reality.

**Warning signals :**
- `rows` estimated very different from `actual rows` (> 2x)
- `cost` very different from `actual time` (> 3x)
- `loops` very high (indicates inefficient join)

**Action :** Always investigate these gaps, they indicate statistics or plan problems.

### ✅ Pitfall avoidance checklist

Before deploying an optimization to production :

- [ ] Statistics up to date (recent `ANALYZE`)
- [ ] Indexes actually used (verify with `EXPLAIN ANALYZE`)
- [ ] Not too many indexes on heavily modified tables
- [ ] Correct column order in multicolumn indexes
- [ ] Expression indexes for functions in WHERE
- [ ] Filter on partition column if table is partitioned
- [ ] No unnecessary `SELECT *`
- [ ] Estimate/reality gaps analyzed and corrected

#### 9.1 Use case 1 : Slow ETL query on logs table

**Context :** Daily ETL pipeline that loads logs into a PostgreSQL table. The transformation query is very slow.

**Initial problem :**
```sql
-- Slow query (30 seconds)
SELECT 
    DATE_TRUNC('hour', log_timestamp) AS hour,
    COUNT(*) AS event_count,
    AVG(duration) AS avg_duration
FROM event_logs
WHERE log_timestamp >= CURRENT_DATE - INTERVAL '7 days'
  AND log_type = 'api_call'
GROUP BY DATE_TRUNC('hour', log_timestamp)
ORDER BY hour;
```

**Diagnosis with EXPLAIN ANALYZE :**
```
Seq Scan on event_logs  (cost=0.00..125000.00 rows=500000 width=16) 
  (actual time=0.123..28500.456 rows=450000 loops=1)
  Filter: ((log_timestamp >= ...) AND (log_type = 'api_call'::text))
  Rows Removed by Filter: 5500000
```

**Analysis :**
- Seq Scan on 6 million rows
- 5.5 million rows filtered (inefficient)
- Execution time : 28.5 seconds

**Applied solutions :**

1. **Create a composite index :**
```sql
CREATE INDEX idx_logs_timestamp_type 
ON event_logs(log_timestamp, log_type);
```

2. **Partition by date (if applicable) :**
```sql
-- If the table is not already partitioned
ALTER TABLE event_logs 
PARTITION BY RANGE (log_timestamp);
```

3. **Update statistics :**
```sql
ANALYZE event_logs;
```

**Result after optimization :**
```
Index Scan using idx_logs_timestamp_type on event_logs  
  (cost=0.43..12500.00 rows=500000 width=16) 
  (actual time=0.045..3200.123 rows=450000 loops=1)
  Index Cond: ((log_timestamp >= ...) AND (log_type = 'api_call'::text))
```

**Gain :** 28.5 seconds → 3.2 seconds (89% gain)

#### 9.2 Use case 2 : Expensive join in a Data Warehouse

**Context :** Reporting query that joins a fact table with several dimensions. Degraded performance.

**Initial problem :**
```sql
-- Slow query (2 minutes)
SELECT 
    d.region,
    d.product_category,
    SUM(f.sales_amount) AS total_sales,
    COUNT(*) AS transaction_count
FROM fact_sales f
JOIN dim_customers c ON f.customer_id = c.customer_id
JOIN dim_products d ON f.product_id = d.product_id
WHERE f.sale_date >= '2025-01-01'
  AND f.sale_date < '2025-02-01'
GROUP BY d.region, d.product_category;
```

**Diagnosis with EXPLAIN ANALYZE :**
```
Nested Loop  (cost=0.00..250000.00 rows=1000000) 
  (actual time=0.123..120000.456 rows=500000 loops=1000)
  -> Seq Scan on fact_sales f
  -> Index Scan using idx_customers_id on dim_customers c
```

**Analysis :**
- Nested Loop with 1000 loops (very expensive)
- Seq Scan on fact table (no index on sale_date)
- Execution time : 120 seconds

**Applied solutions :**

1. **Index the join and filter column :**
```sql
CREATE INDEX idx_fact_sales_date_customer 
ON fact_sales(sale_date, customer_id);
CREATE INDEX idx_fact_sales_product 
ON fact_sales(product_id);
```

2. **Partition the fact table by date :**
```sql
-- If not already done
ALTER TABLE fact_sales 
PARTITION BY RANGE (sale_date);
```

3. **Force a Hash Join if appropriate :**
```sql
SET enable_nestloop = off;  -- Temporarily to test
-- Or let PostgreSQL choose with better statistics
```

**Result after optimization :**
```
Hash Join  (cost=15000.00..25000.00 rows=1000000) 
  (actual time=500.123..8500.456 rows=500000 loops=1)
  Hash Cond: (f.customer_id = c.customer_id)
  -> Index Scan using idx_fact_sales_date_customer on fact_sales f
  -> Hash
     -> Seq Scan on dim_customers c
```

**Gain :** 120 seconds → 8.5 seconds (93% gain)

#### 9.3 Use case 3 : Analytical query on JSONB

**Context :** Table storing events in JSONB. Slow search queries.

**Initial problem :**
```sql
-- Slow query (15 seconds)
SELECT 
    event_id,
    event_data->>'user_id' AS user_id,
    event_data->>'action' AS action
FROM events
WHERE event_data->>'action' = 'purchase'
  AND event_data->>'timestamp' >= '2025-01-01';
```

**Diagnosis :**
```
Seq Scan on events  (cost=0.00..50000.00 rows=10000 width=64) 
  (actual time=0.123..15000.456 rows=8500 loops=1)
  Filter: (((event_data ->> 'action'::text) = 'purchase'::text) AND ...)
```

**Applied solutions :**

1. **Create a GIN index on JSONB :**
```sql
CREATE INDEX idx_events_data_gin ON events USING GIN (event_data);
```

2. **Use optimized JSONB operators :**
```sql
-- Optimized query
SELECT 
    event_id,
    event_data->>'user_id' AS user_id,
    event_data->>'action' AS action
FROM events
WHERE event_data @> '{"action": "purchase"}'::jsonb
  AND (event_data->>'timestamp')::timestamp >= '2025-01-01'::timestamp;
```

**Result after optimization :**
```
Bitmap Index Scan on idx_events_data_gin  (cost=0.00..500.00 rows=10000) 
  (actual time=0.045..250.123 rows=8500 loops=1)
  Index Cond: (event_data @> '{"action": "purchase"}'::jsonb)
```

**Gain :** 15 seconds → 0.25 seconds (98% gain)

## 📝 Expected answers and detailed explanations

### Exercise 1 : Simple execution plan

#### Typical execution plan with EXPLAIN

```
Seq Scan on orders  (cost=0.00..18.10 rows=2 width=40)
  Filter: (amount > 700::numeric)
```

#### Detailed analysis

**1. Scan type : Seq Scan**

PostgreSQL chooses a **Sequential Scan** because :
- The table contains only 3 rows (too small for an index to be profitable).
- The cost of reading the index would be higher than the cost of sequential read of the entire table.
- General rule : on tables with less than ~100 rows, PostgreSQL often prefers a Seq Scan.

**2. Cost interpretation (`cost=0.00..18.10`)**

- **0.00** (startup cost) : cost before getting the first row. Here, very low because no sorting or complex preparation.
- **18.10** (total cost) : total estimated cost to return all rows.
- **Unit** : cost is relative, based on configuration parameters (`seq_page_cost`, `cpu_tuple_cost`, etc.).
- **Comparison** : a cost of 18.10 is very low. In production, we generally worry about costs > 1000-10000.

**3. Estimated rows (`rows=2`)**

- PostgreSQL estimates that 2 rows out of 3 match the filter `amount > 700`.
- This estimate is based on statistics collected by `ANALYZE`.
- On a 3-row table, the estimate is approximate because statistics are limited.

**4. Plan with EXPLAIN ANALYZE**

```
Seq Scan on orders  (cost=0.00..18.10 rows=2 width=40) 
  (actual time=0.012..0.015 rows=2 loops=1)
  Filter: (amount > 700::numeric)
  Rows Removed by Filter: 1
```

**Real metrics analysis :**
- **actual time=0.012..0.015** : 
  - 0.012 ms to get the first row
  - 0.015 ms to get all rows
  - Very low time because the table is tiny
- **actual rows=2** : 2 rows returned (matches the estimate)
- **loops=1** : the scan was executed once
- **Rows Removed by Filter: 1** : 1 row was filtered (the one with `amount=500`)

**5. Estimate/reality gap**

On this 3-row table :
- The gap is negligible because the table is too small for statistics to be significant.
- **In production** : a large gap between `rows` and `actual rows` (ex: 1000 estimated vs 10000 actual) indicates :
  - Obsolete statistics → execute `ANALYZE table_name`
  - Non-uniform data distribution → adjust `default_statistics_target`
  - Selectivity problem → check indexes and filters

### Exercise 2 : Observing index impact

#### Plan before index (Seq Scan)

```
Seq Scan on orders  (cost=0.00..18.10 rows=2 width=40) 
  (actual time=0.012..0.015 rows=2 loops=1)
  Filter: (amount > 700::numeric)
```

#### Plan after index (on 3-row table)

```
Seq Scan on orders  (cost=0.00..18.10 rows=2 width=40) 
  (actual time=0.011..0.014 rows=2 loops=1)
  Filter: (amount > 700::numeric)
```

**Important observation :** On a 3-row table, PostgreSQL may **still choose a Seq Scan** even with an index, because :
- The cost of reading the index (2-3 pages) + table access is higher than the cost of sequential read (1 page).
- This is normal and optimal planner behavior.

#### Plan after index (on 10,000-row table)

On a larger table, you would see :

**Without index :**
```
Seq Scan on orders  (cost=0.00..431.00 rows=2000 width=40) 
  (actual time=0.123..45.234 rows=1987 loops=1)
  Filter: (amount > 3000::numeric)
  Rows Removed by Filter: 8013
```

**With index :**
```
Index Scan using idx_orders_amount on orders  
  (cost=0.29..85.47 rows=2000 width=40) 
  (actual time=0.045..12.567 rows=1987 loops=1)
  Index Cond: (amount > 3000::numeric)
```

#### Comparative analysis

**1. Scan change**

- **Before** : Seq Scan (read all rows)
- **After** : Index Scan (targeted read via index)
- **Why** : on 10,000 rows, the index allows quickly locating ~2000 concerned rows without scanning the other 8000.

**2. Performance gain**

**Comparative metrics :**
- **Estimated cost** : 431.00 → 85.47 (~80% reduction)
- **Real time** : 45.234 ms → 12.567 ms (~72% reduction)
- **Rows scanned** : 10,000 → ~2000 (80% reduction)

**Improvement ratio calculation :**
```
Ratio = time_without_index / time_with_index
Ratio = 45.234 / 12.567 ≈ 3.6x faster
```

**3. When a Seq Scan is preferable**

A Seq Scan becomes preferable when :
- **More than 5-10% of the table is returned** : sequential read cost becomes lower than indexed access cost.
- **Very small table** (< 100 rows) : index overhead not profitable.
- **No index available** : obviously, PostgreSQL has no choice.
- **Query requires majority of columns** : Index Scan requires additional table accesses.

**Concrete example :**
```sql
-- Returns 80% of the table → Seq Scan preferred
SELECT * FROM orders WHERE amount > 100;

-- Returns 2% of the table → Index Scan preferred
SELECT * FROM orders WHERE amount > 4500;
```

### Exercise 4 : Real case with large volumes (Data Engineer)

#### Scenario : 10,000-row table

**1. Plan without index**

```
Seq Scan on orders  (cost=0.00..431.00 rows=2000 width=40) 
  (actual time=0.123..45.234 rows=1987 loops=1)
  Filter: (amount > 3000::numeric)
  Rows Removed by Filter: 8013
```

**Detailed analysis :**
- **Cost** : 431.00 (high because scans all rows)
- **Real time** : 45.234 ms
- **Rows scanned** : 10,000 (all)
- **Rows returned** : 1987 (~20% selectivity)
- **Efficiency** : 80% of rows are filtered (inefficient)

**2. Plan with index**

```
Index Scan using idx_orders_amount on orders  
  (cost=0.29..85.47 rows=2000 width=40) 
  (actual time=0.045..12.567 rows=1987 loops=1)
  Index Cond: (amount > 3000::numeric)
```

**Detailed analysis :**
- **Cost** : 85.47 (80% reduction)
- **Real time** : 12.567 ms (72% reduction)
- **Rows scanned** : ~2000 (via index, then table access)
- **Rows returned** : 1987
- **Efficiency** : scans only relevant rows

**3. Quantitative comparison**

| Metric | Without index | With index | Improvement |
|--------|---------------|------------|-------------|
| **Estimated cost** | 431.00 | 85.47 | -80% |
| **Real time** | 45.234 ms | 12.567 ms | -72% |
| **Rows scanned** | 10,000 | ~2,000 | -80% |
| **Improvement ratio** | 1x | 3.6x | **+260%** |

**4. Selectivity impact**

**Low selectivity query (`amount > 100` - returns 80% of rows) :**

```
Seq Scan on orders  (cost=0.00..431.00 rows=8000 width=40) 
  (actual time=0.123..38.456 rows=7987 loops=1)
  Filter: (amount > 100::numeric)
```

- PostgreSQL chooses **Seq Scan** because 80% of the table is returned.
- An Index Scan would be less efficient (too many table accesses).

**Highly selective query (`amount > 4500` - returns 2% of rows) :**

```
Index Scan using idx_orders_amount on orders  
  (cost=0.29..12.34 rows=200 width=40) 
  (actual time=0.045..2.123 rows=187 loops=1)
  Index Cond: (amount > 4500::numeric)
```

- PostgreSQL chooses **Index Scan** because only 2% of the table is returned.
- Even greater gain : 2.123 ms vs 45.234 ms (21x faster).

**5. Selectivity threshold**

**Empirical rule :**
- **< 5% of rows returned** : Index Scan generally preferred
- **5-10% of rows returned** : depends on table size and indexes
- **> 10% of rows returned** : Seq Scan often preferred

**Calculation for your case :**
```sql
-- Selectivity = rows returned / total rows
-- amount > 3000 : 1987 / 10000 = 19.87% → Seq Scan may be preferred
-- amount > 4500 : 187 / 10000 = 1.87% → Index Scan preferred
```

**6. ETL impact in production**

**Real scenario : Daily pipeline with 10 million rows**

**Without index :**
- Execution time : ~10 minutes
- Resources : high CPU, significant disk I/O
- Impact : pipeline slows down following processes

**With index :**
- Execution time : ~1 minute
- Resources : moderate CPU, reduced disk I/O
- Impact : efficient pipeline, other processes not affected

**Gain calculation :**
```
Gain = (time_without_index - time_with_index) / time_without_index × 100
Gain = (10 - 1) / 10 × 100 = 90%
```

**Index maintenance cost :**
- Creation : ~2-5 minutes (once)
- Maintenance : +10-20% on INSERT/UPDATE (acceptable)
- **ROI** : 9 minutes gain per execution → very profitable on a daily pipeline

**7. Data Engineer recommendations**

**When to create an index :**
- Columns frequently filtered in ETL queries
- Join keys to optimize JOINs
- Columns used in ORDER BY on large volumes
- Columns with high selectivity (< 10%)

**When to avoid an index :**
- Very low selectivity columns (ex: boolean with 50/50)
- Very small tables (< 1000 rows)
- Very frequently modified columns (high maintenance cost)
- Tables with many INSERTs (write slowdown)

**Production monitoring :**
```sql
-- Check index usage
SELECT * FROM pg_stat_user_indexes 
WHERE idx_scan = 0;  -- Never used indexes

-- Check statistics
SELECT schemaname, tablename, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
WHERE last_analyze IS NULL OR last_analyze < NOW() - INTERVAL '7 days';
```

## 💡 Advanced tips for self-learning

### 1. Experiment with different volumes

**Recommended progression :**
- **100 rows** : understand basics, see simple plans
- **1,000 rows** : observe first gains with indexes
- **10,000 rows** : see real impact of optimizations
- **100,000 rows** : simulate production cases
- **1,000,000+ rows** : understand very large volume challenges

**Script to generate different volumes :**
```sql
-- Adjust the number in generate_series(1, N)
INSERT INTO orders (customer_id, order_date, amount, status)
SELECT 
    (random() * 1000)::int,
    '2025-01-01'::date + (random() * 365)::int,
    (random() * 5000)::numeric(10,2),
    CASE WHEN random() > 0.5 THEN 'active' ELSE 'inactive' END
FROM generate_series(1, 100000);  -- Change the number here
```

### 2. Test different selectivities

**Experimentation strategy :**
- **10% selectivity** : `WHERE amount > 4500` (on 10k rows = ~1000 rows)
- **50% selectivity** : `WHERE amount > 2500` (on 10k rows = ~5000 rows)
- **90% selectivity** : `WHERE amount > 500` (on 10k rows = ~9000 rows)

**Observe :**
- Planner choice (Seq Scan vs Index Scan)
- Execution times
- Estimated costs

### 3. Compare EXPLAIN vs EXPLAIN ANALYZE

**Methodology :**
1. Execute `EXPLAIN` to see estimates
2. Execute `EXPLAIN ANALYZE` to see reality
3. Compare `rows` vs `actual rows`
4. Compare `cost` vs `actual time`

**Warning signals :**
- `rows` gap > 2x : statistics need updating
- `cost/time` gap > 3x : configuration or statistics problem
- `actual time` much higher than expected : bottleneck to identify

### 4. Use \timing in psql

**Activation :**
```sql
\timing on
```

**Usage :**
```sql
SELECT * FROM orders WHERE amount > 3000;
-- Displays : Time: 45.234 ms
```

**Advantages :**
- Measures real execution time (includes network time, display, etc.)
- Simpler than `EXPLAIN ANALYZE` for quick comparisons
- Useful for measuring global impact of an optimization

### 5. Diagnostic best practices

**Optimization checklist :**
- [ ] Statistics up to date (recent `ANALYZE`)
- [ ] Existing and used indexes (`pg_stat_user_indexes`)
- [ ] Appropriate selectivity (efficient filters)
- [ ] Analyzed execution plans (`EXPLAIN ANALYZE`)
- [ ] Compared metrics (before/after optimization)
- [ ] Impact measured in production (monitoring)

**Complementary tools :**
- `pg_stat_statements` : identify most expensive queries
- `explain.dalibo.com` : graphical plan visualization
- `pgBadger` : PostgreSQL log analysis
- Monitoring (Grafana, Datadog) : real-time performance tracking
